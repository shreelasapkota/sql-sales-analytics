# Design — SQL Sales Analytics

**Date:** 2026-08-10
**Status:** Approved, in progress

## Goal

Demonstrate advanced analytical SQL — window functions, CTEs, ranking, trend analysis,
partition-based calculations, and query optimization — on a realistic dataset, in a form
that can be explained and defended in an interview.

Correctness and explanation quality matter more than query count.

## Dataset

**Olist Brazilian E-Commerce Public Dataset** — ~100k orders placed on a Brazilian
marketplace between September 2016 and October 2018.

Kaggle requires authentication, so the loader pulls from a public HuggingFace mirror
(`aviahYadler/Olist_Ecommerce_Dataset`). The mirror was verified against the canonical
row counts of the original Kaggle release before being adopted:

| File | Rows | Verified |
|---|---:|---|
| olist_customers_dataset | 99,441 | yes |
| olist_geolocation_dataset | 1,000,163 | yes |
| olist_order_items_dataset | 112,650 | yes |
| olist_order_payments_dataset | 103,886 | yes |
| olist_order_reviews_dataset | 99,224 | yes |
| olist_orders_dataset | 99,441 | yes |
| olist_products_dataset | 32,951 | yes |
| olist_sellers_dataset | 3,095 | yes |
| product_category_name_translation | 71 | yes |

All nine match the original exactly. Northwind fallback was not needed.

## Data profiling findings

These were measured from the raw CSVs before the schema was written. Each one changed a
design decision.

| Finding | Consequence |
|---|---|
| `review_id` has 98,410 distinct values across 99,224 rows | `review_id` alone cannot be the primary key. `(review_id, order_id)` is unique and is used instead. |
| Zip prefixes are 5-char and 245,733 begin with `0` | Zip columns are `CHAR(5)`, never integer. An integer column would destroy leading zeros and break the Day 3 prefix rollup. |
| 2 of 73 product categories have no English translation | No foreign key from `products` to the translation table. Queries use `LEFT JOIN` + `COALESCE`; an inner join would silently drop revenue. |
| 610 products have a blank category | Category is nullable. Ranking queries must decide explicitly whether to include them. |
| `geolocation` has 261,831 fully duplicate rows and 19,015 distinct zips | Loaded faithfully with no primary key. Joining it naively to orders multiplies revenue — a documented trap. |
| 2,965 orders have no delivery date | Delivery timestamps are nullable. Delivery-time math must exclude them, not treat them as zero. |
| 99,441 `customer_id` vs 96,096 `customer_unique_id` | `customer_id` is per-order; `customer_unique_id` identifies the person. Lifetime-value work must group by the latter. |
| Source CSV misspells `product_name_lenght` | Corrected to `product_name_length` in the schema; documented as a deliberate rename. |
| Translation CSV carries a UTF-8 BOM | Loader reads it with `utf-8-sig`. |
| Zero orphan rows across every candidate foreign key | All foreign keys are declared and enforced for real. |

## Schema

Nine tables mirroring the source files. No invented data.

| Table | Role | Primary key |
|---|---|---|
| `customers` | One row per order-placer. `customer_unique_id` is the real person. | `customer_id` |
| `orders` | Order lifecycle with five timestamps. | `order_id` |
| `order_items` | Line items. Grain: one row per item per order. | `(order_id, order_item_id)` |
| `order_payments` | Payment records; orders may split across methods. | `(order_id, payment_sequential)` |
| `order_reviews` | 1–5 score plus free-text comments. | `(review_id, order_id)` |
| `products` | Product dimensions and category. | `product_id` |
| `sellers` | Marketplace sellers. | `seller_id` |
| `geolocation` | Zip prefix to lat/lng. Many rows per zip. | none (by design) |
| `product_category_translation` | Portuguese to English category names. | `product_category_name` |

### Type choices

- **Money** is `NUMERIC(10,2)`, never `float`. Binary floating point cannot represent
  decimal currency exactly, and summing it across 112k line items accumulates error.
- **Latitude/longitude** are `DOUBLE PRECISION`. These are measurements, not money;
  approximation is acceptable and arithmetic is faster.
- **Zip prefixes** are `CHAR(5)` to preserve leading zeros.
- **Timestamps** are `TIMESTAMP` without time zone, because the source carries no offset.
  Inventing one would be a false precision claim.

### Load strategy

Create tables and primary keys, `COPY` the data in, *then* add foreign keys and indexes.

Adding constraints after a bulk load is substantially faster than validating them row by
row during insert, and it produces a measurable before/after for `optimization.md`.

### Index strategy

Day 1 creates only primary keys and indexes on foreign key columns. PostgreSQL does not
automatically index the referencing side of a foreign key, and every analytical query
joins on them.

Composite and covering indexes are deliberately deferred to Day 3, so the optimization
pass has genuine `EXPLAIN ANALYZE` improvements to demonstrate rather than staged ones.

## Recursive CTE approach

Olist has no natural hierarchy: categories are a flat list of 73 and geography is flat
zip/city/state. Rather than invent a mapping table, the recursive CTE walks a **zip-prefix
rollup** derived entirely from real data:

```
state (SP) -> 2-digit region (01) -> 3-digit sector (010) -> 5-digit prefix (01001)
```

Every level comes from the actual `geolocation` and `customers` tables. Nothing is fabricated.

## Non-goals

- No dashboard, BI layer, or visualization.
- No ORM or application code. This is a SQL project.
- No data cleaning beyond what is documented above. The gotchas are the interesting part
  and are preserved, not scrubbed away.
